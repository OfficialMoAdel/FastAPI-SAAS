# FastAPI_saas-vpbi — evidence reconciliation

Preserved 2026-10-19. Source: `/home/ansible/ab/evidence_20261015/` on
`perf-local` (ansible@192.168.121.147).

These ten files were the sole evidence for the `vpbi` close-out, and they lived
only in a home directory on one load-test host, outside git. That made the
P-22 verdict and the close itself unfalsifiable: reset the box and the close has
nothing behind it. They are here so the claim can be checked rather than
trusted. Nothing in this directory was generated by this reconciliation; every
file is byte-for-byte what the 2026-10-15 session left behind.

## The question vpbi was asked

`r8hz` (P-22) closed WITHOUT PASSING: its acceptance criterion was a
discriminating A/B whose delta exceeds the noise floor, and that measurement was
never produced. `vpbi` inherited it and was asked to run the single cheap
measurement, then the A/B, and report four quadrants.

## What was verified, and how

Read-only. Percentiles were recomputed from the raw `server_side.samples_ms`
arrays using the repository's own `src/benchmarks.percentiles.nearest_rank`,
imported rather than reimplemented, so a difference in percentile convention
could not manufacture a disagreement.

**Every one of the eight numeric claims in `vpbi`'s close notes reproduces**, to
a delta of 0.0005 or better: `client_p95_ratio` 1.193, `server_p95_ratio`
1.0668, before/after server p99 23.939 / 60.507 ms, p99 ratio 2.5275, server max
ratio 6.4696. Both floor comparisons hold as stated (2.527 > the 2.0 intra-arm
floor; 6.47 < the 7.1 run-to-run floor). The close notes are arithmetically
honest.

**The split-import blocker was genuinely resolved.** Both raw exports carry
`src_app_from` pointing at their own worktree — `/home/ansible/ab/before/src` on
port 8021, `/home/ansible/ab/after/src` on port 8022 — so the arms were running
their own source, not a shared editable install. That was `vpbi`'s inherited
blocker and the bytes confirm it was fixed rather than merely reported fixed.

## The finding: two artefact generations, and the quoted run is the weakest

The directory holds two different artefact formats. The distinction matters
because only one of them carries the harness's own classification.

**Generation 1 — the harness's own reports** (`short_run.json`,
`qualifying_run.json`, `wyjb_verify.json`). All three carry exactly the nine
top-level keys `scripts/ab_users_me.py::build_artefact` emits today:
`artefact`, `generated_by`, `question`, `arms`, `delta`, `client_p95_ratio`,
`server_p95_ratio`, `gate_a_compliance`, `instrument`. Per arm they record
`client_observed_ms`, `server_side_ms`, `status_counts`, `pooled_n`, `loop_lag`,
`loop_lag_note`, and — from `wyjb_verify` onward — `src_app_from` and
`server_instrument`. Their per-arm key sets differ (13 in
`qualifying_run.json`, 14 in `short_run.json`'s before arm, 15 in
`wyjb_verify.json`) because they were produced by three different versions of
the script; the current script's 15 per-arm keys match `wyjb_verify.json`.
There is no reducer between the harness and these files.

**Generation 2 — raw instrument exports** (`before_arm.json`, `after_arm.json`,
`final_before_arm.json`, `final_after_arm.json`). Five top-level keys only:
`worktree`, `port`, `src_app_from`, `server_side{instrument, header, count,
samples_ms[]}`, and `loop_lag{...}`. **No `delta` (the harness's
classification), no ratios, no load configuration, and no client-side
observations.**

Two things follow, and they cut in opposite directions from the close notes.

**First: the run the notes quote is the only report that is both the null AND
the pre-instrument run.** `qualifying_run.json` has `loop_lag: None` together
with an explicit `loop_lag_note` string, and it has no `src_app_from` and no
`server_instrument` keys at all. `wyjb_verify.json` has `loop_lag` fully
populated, `loop_lag_note: None`, and both new fields. The server-side sampler
landed between them. So the reported p95 of 1.0668 comes from the one report that
predates the instrument that measures the server-side view — and the report
generated after that instrument landed says the opposite, in the harness's own
words.

**Second: the largest and best-instrumented data in the directory was never
reduced to a report.** The 17:33 export pair has n=10490 server-side samples in
each arm, `loop_lag` at 125 Hz with `meets_minimum_rate` true and 65536 samples,
and `src_app_from` present — strictly better instrumented than anything the
reports were built from. It has no verdict because no report was ever generated
from it. The 2.61× p95, 3.15× p99 and 3.61× p50 figures for that pair are
figures recomputed during this reconciliation from raw samples, not figures the
harness issued.

That last recomputation also contradicts a claim in the close notes. The notes
attribute the regression to per-request CPU densification and say p50 hides it
because the path is I/O-dominated. The 17:33 pair shows p50 at 3.61×, which is
not hidden. Either the notes' mechanism statement does not hold for the run with
the most samples, or the p50 statement was written about a different run.

## Why no run in this directory is the record of the verdict

Three reports, three verdicts, and the artefacts do not decide between them:

- `short_run` is a null, but at 8 accounts and before the instrument.
- `qualifying_run` is a null on p95, and is demonstrably the pre-instrument run.
- `wyjb_verify` is positive, and is the post-instrument run.

Picking the qualifying run because it is the one the notes quote would repeat
the selection error. Promoting `wyjb_verify` because it is the most
instrumented *report* would discount the two raw exports, which are better
instrumented still. Promoting the 17:33 exports because they have the most
samples would replace one unjustified selection with another — and there is a
recorded reason for doubt, not merely an absence of one: on this same host,
three days ago, a single non-interleaved run showed monotonic inflation
(149 µs → 529 µs across repetitions) that had to be attributed to the host and
discarded. The 17:33 exports come from a single round with no interleaved
repeat, which is exactly the design that produced that drift.

The exports carry no load configuration, so the ~20 ms versus ~345 ms p95
difference between the report-era runs and the export-era runs cannot be
attributed to either load shape or host drift from these files alone. Stating
either cause would be a guess.

## What cannot be recovered from this directory

- **Q1, the client view, is unrecoverable from the exports.** They record no
  `client_observed_ms`. The four-quadrant report cannot be reconstructed from
  them; only the server-side questions (Q2 p95, Q3 loop lag, Q4 p99 and max) can
  be recomputed. Q1 was already VOID on co-location grounds, so nothing is lost
  in practice — but it means the exports are not a substitute for the reports.
- **GATE A compliance is unevaluable against the exports.** Criteria 5
  (production budgets), 6 (zero rate-limit events) and 9 (five repetitions) all
  require the load configuration, which the export format does not record. Only
  the generation-1 reports carry a `gate_a_compliance` block.

## What a verdict would require

A fresh A/B from the harness, interleaved — alternate arms across rounds rather
than running one arm to completion — so that a monotonic host drift cannot be
mistaken for a treatment effect. The instrument, the harness and both worktrees
already exist; what is missing is a run whose arms are comparable by
construction rather than by argument.

Producing one generates load on a load-test host, so it is a decision for the
owner rather than an inference from this directory.

## Status of P-22

Unchanged by this reconciliation, and deliberately so. `r8hz` closed "without
passing" and `vpbi` closed against evidence that is weaker than it appears: the
quoted run is the pre-instrument one, and the stronger data was never reduced to
a report. "Closed without passing" remains a defensible resting state on this
evidence. Re-scoring a gate is the owner's decision.

## Corrections made during this reconciliation

Recorded because two earlier readings of this same directory were wrong and are
worth not repeating:

- An initial probe reported `worktree`, `src_app_from` and `port` as absent from
  `qualifying_run.json`. They are not absent: generation-1 reports carry
  `worktree` **per arm**, and the probe looked only at the top level. The
  qualifying run records its worktree; it lacks `src_app_from` and
  `server_instrument` because it predates them.
- An initial reading concluded the 17:33 pair sat in a different performance
  regime, implying host drift. That conclusion is not supported: the pair is a
  raw export, not a fourth report, and the difference is at least as plausibly
  load shape as drift. This file therefore asserts neither.
